SECTION 1  
SYSTEM OVERVIEW &amp; ARCHITECTURE
1.1 Purpose &amp; Business Context
The Return Logistics Tracking System (RLTS) is a multi-platform digital solution designed to eliminate the friction, paper trails, and disputes that arise during product return cycles between Dealers, CFA (Carrying &amp; Forwarding Agents), and the Company. Every return is tracked end-to-end with photographic proof, digital signatures, GPS verification, and a timestamped audit trail.
1.2 Core Users &amp; Their Pain Points
DEALER PROBLEMS (solved)
No visibility once product leaves their premises
Disputes over whether pickup happened or not
Delayed refunds with no tracking
No proof of product condition at handover
Manual paperwork that gets lost
COMPANY PROBLEMS (solved)
CFA agents not accountable for pickups
No centralized view of all returns
Fake refund claims without proof
Inability to track product condition on return
Audit failures due to missing documentation

SECTION 2  
AUTHENTICATION &amp; AUTHORIZATION
2.1 Authentication Flow
All three platforms (Dealer App, CFA App, Admin Panel) use the same JWT-based authentication system. Tokens are short-lived (24 hours) with refresh tokens (7 days). All API routes except /api/auth/login require a valid Bearer token.
Login Process
User enters email + password
Backend validates credentials against hashed password (bcrypt, 12 rounds)
If valid: return accessToken (24h) + refreshToken (7d) + user object with role
If invalid: return 401 with generic message (never reveal which field is wrong)
Store tokens securely: Flutter uses flutter_secure_storage, React uses httpOnly cookies or memory
All subsequent requests include: Authorization: Bearer &lt;accessToken&gt;

2.2 Security Requirements
Passwords hashed with bcrypt (minimum 12 salt rounds). Never store plaintext.
JWT secret must be minimum 256-bit random string, stored in environment variable.
Access tokens: 24h expiry. Refresh tokens: 7 days. On logout, invalidate refresh token.
Rate limit login endpoint: max 5 attempts per IP per 15 minutes. Return 429 with retry-after header.
All API inputs must be validated and sanitized. Reject requests with unexpected fields.
HTTPS enforced on all endpoints. HTTP redirects to HTTPS.
CORS configured with strict allowlist (not wildcard).
Helmet.js for HTTP security headers.
File uploads: validate MIME type server-side, not just extension. Max file size: 10MB.
Audit log every sensitive action (role change, approve, reject, refund).

SECTION 4  
COMPLAINT STATUS WORKFLOW
4.1 Status Lifecycle
Every complaint follows a strict linear progression. No skipping of steps is permitted. Every status change is recorded in the timeline array with timestamp, actor, and optional note.
CREATED
Dealer submits complaint
→ Transitions to: APPROVED
APPROVED
Admin approves complaint
→ Transitions to: CFA_ASSIGNED
CFA_ASSIGNED
Admin assigns CFA agent
→ Transitions to: PICKED_UP
PICKED_UP
CFA collects product
→ Transitions to: RECEIVED_AT_CFA
RECEIVED_AT_CFA
Product at CFA warehouse
→ Transitions to: VERIFIED
VERIFIED
Admin verifies product
→ Transitions to: REFUND_PROCESSED
REFUND_PROCESSED
Refund issued to dealer
Terminal state
4.2 Status Transition Rules
CREATED → APPROVED or REJECTED
Actor: Admin only. Admin must review complaint details and images. On approval, system auto-generates QR code if not already created. On rejection, admin must provide rejectionReason (min 10 chars). Dealer receives email notification either way.
APPROVED → CFA_ASSIGNED
Actor: Admin only. Admin selects a CFA from the region-matched list. System sets cfaId and estimatedPickupDate. CFA receives push notification and email with complaint details. Dealer is notified that pickup is scheduled.
CFA_ASSIGNED → PICKED_UP
Actor: CFA only. CFA must: (1) scan QR code or enter Complaint ID, (2) upload min 1 pickup photo, (3) capture dealer signature, (4) capture GPS location. All four steps mandatory. System creates PickupProof document. Dealer notified with proof link.
PICKED_UP → RECEIVED_AT_CFA
Actor: CFA only. CFA must: (1) upload min 1 warehouse photo, (2) confirm received quantity (must match complaint quantity or flag discrepancy). System updates PickupProof with warehouse data. Admin notified for verification.
RECEIVED_AT_CFA → VERIFIED
Actor: Admin only. Admin reviews all proof: pickup photos, warehouse photos, signature, GPS, quantity confirmation. Admin can add adminNotes. If discrepancy found, admin can flag and communicate manually. System moves to VERIFIED.
VERIFIED → REFUND_PROCESSED
Actor: Admin only. Admin enters refundAmount (INR), refundReference (bank/UPI reference), and optional note. System records exact refundDate. Dealer receives email with refund details. This is the terminal state.

9.2 Upload Rules
All uploads go through backend. Never allow direct client-to-S3 (no pre-signed PUT from mobile).
Backend validates: MIME type (image/jpeg, image/png only), max file size 10MB.
Images auto-compressed to max 1920px wide, 85% JPEG quality using sharp npm package.
S3 objects are private. Served via CloudFront with signed URLs (expiry: 24 hours).
File naming: {complaintId}_{timestamp}_{randomUUID}.jpg — prevents path traversal.
On complaint rejection or deletion (soft), S3 objects are NOT deleted (audit trail).
9.3 QR Code Generation
Generated server-side using qrcode npm package when complaint status moves to APPROVED.
QR code encodes: complaint ID string (e.g. CMP-2024-0042).
Saved as PNG to S3 at complaints/{complaintId}/qr-code/qr.png.
QR code URL returned in complaint detail API response.
Mobile CFA app uses mobile_scanner to decode. Backend validates the decoded ID.

10.2 HTTP Status Code Usage
Code
When to use
200 OK
Successful GET, PUT, DELETE
201 Created
Successful POST that creates a new resource (complaint, user)
400 Bad Request
Validation errors, missing required fields, invalid format
401 Unauthorized
Missing or invalid JWT token
403 Forbidden
Valid token but insufficient role permissions
404 Not Found
Resource ID does not exist in database
409 Conflict
Duplicate creation (e.g. email already exists)
422 Unprocessable
Business rule violation (e.g. wrong status transition)
429 Too Many Requests
Rate limit exceeded. Include Retry-After header.
500 Internal Error
Unexpected server error. Never expose stack trace in production.
10.3 Input Validation Rules
Email: valid RFC 5322 format. Lowercase before storage.
Password: minimum 8 chars, must contain uppercase, lowercase, and digit.
Complaint ID format: strictly CMP-YYYY-XXXX where YYYY is 4-digit year and XXXX is zero-padded sequential 4-digit number.
Quantity: integer, min 1, max 10000. Reject decimals.
Image files: MIME type must be image/jpeg or image/png. Magic bytes validated server-side.
GPS coordinates: latitude -90 to 90, longitude -180 to 180. Both required together.
Date fields: ISO 8601 format. Estimated pickup date must be in the future.
Refund amount: positive number, max 2 decimal places, max INR 10,00,000.
All string fields: strip HTML tags, trim whitespace. Store sanitized.

SECTION 14  
CRITICAL BUSINESS RULES
14.1 Complaint Rules
A dealer can have a maximum of 10 OPEN (non-terminal) complaints at any time. 11th submission is rejected with 429 message.
Complaint ID is generated as CMP-{YEAR}-{SEQUENCE} where SEQUENCE is a global auto-increment per year, zero-padded to 4 digits. Reset to 0001 each January 1st.
A complaint cannot be re-opened after REFUND_PROCESSED or REJECTED. Dealer must create a new complaint.
Images must be uploaded fresh at the time of complaint creation. Pre-existing S3 URLs are not accepted.
Quantity in PickupProof (receivedQuantity) must match complaint quantity. If it does not, admin is flagged and must review before verification.
14.2 CFA Assignment Rules
Admin can only assign a CFA whose region matches the dealer&apos;s region. API enforces this.
A CFA agent can have a maximum of 20 active (non-terminal) complaints assigned at one time.
If a CFA is deactivated while having active assignments, admin must reassign each complaint manually.
CFA cannot mark pickup if current status is not exactly CFA_ASSIGNED.
14.3 Refund Rules
Refund can only be processed on a complaint in VERIFIED status.
Refund amount must be entered by admin (system does not auto-calculate).
Refund reference number is mandatory — serves as audit proof.
Once REFUND_PROCESSED, the complaint is fully closed and immutable.
